# 信任与抗投毒设计

## 威胁模型

平台假设以下参与者可能主动对抗检测：

- 中转提供商识别公开探针，在检测时临时路由到真实模型。
- 提供商识别项目节点、固定时间、固定账号或固定请求序列。
- 攻击者批量提交伪造的通过或失败样本操纵排名。
- 贡献者修改基线、阈值或评分逻辑，使特定提供商获益。
- 捐赠 key 被植入特殊路由，不能代表普通客户体验。
- 旧证据被选择性删除，或新短期样本掩盖长期异常。

## 证据分层

| 层级 | 来源 | 对正式评级的影响 |
| --- | --- | --- |
| A 正式审计 | 项目控制的账号、预算和签名执行节点 | 可影响评级 |
| B 可信社区 | 身份和节点经过验证、历史稳定、可独立复现 | 满足覆盖与复现门槛后可影响评级 |
| C 匿名捐赠 | 匿名 key、账号或一次性样本 | 仅作线索；失败触发复核，通过不加分 |
| D 提供商自报 | 提供商控制的账号、节点或提交 | 单独展示；通过不加分 |

四类证据不得汇总成一个多数票。Dashboard 必须同时展示分层数量和覆盖，而非只显示总样本数。

## 降低选择性路由收益

1. **分布式执行**：使用多个地区、ASN、云厂商和住宅/机构网络，但不公开实时节点清单。
2. **独立账号**：项目自行购买账号，并与可信社区、匿名捐赠账号交叉比较。
3. **随机调度**：使用时间抖动、请求顺序变化、短/长上下文和普通/Native 多种模式。
4. **探针族轮换**：公开方法与评分原则，延迟公开仍在使用的具体探针实例。
5. **蜜罐对照**：混合不计分的对照任务，使对手难以识别正式测试窗口。
6. **路径对比**：比较中心节点与分布式节点、项目账号与用户账号、官方与第三方路径。
7. **延迟结论**：等待跨时间、跨账号和跨节点复现后再提升严重等级。

这些措施只能提高投毒成本，不能证明没有选择性路由。

## 结论规则

- 使用“未观察到异常”“证据冲突”“疑似选择性路由”“观察到高风险差异”等有限结论。
- A/B 层独立来源达到预设覆盖和复现门槛后，才允许改变正式状态。
- C/D 层通过结果永远不能抵消 A/B 层失败。
- C/D 层失败先进入隔离队列；只有 A/B 层复现后才进入公开正式证据。
- 中心任务通过而多个分布式任务失败时，标记疑似选择性路由并扩大抽样。
- 严重事件保留在历史中；状态恢复需要显示恢复窗口，不能删除原事件。
- 每条结论绑定模型快照、探针版本、评分版本和有效期。

## 社区提交防护

- 结构化 schema 校验、字段范围校验、签名与来源记录。
- 新账号、同网络、同指纹或高度相关的批量样本降权和限速。
- 变更必须以字段 diff 提交，说明原因并附可复核证据。
- 基线和评分变更至少双人审核；高影响变更要求阈值签名。
- `beta` 必须经过多个独立来源复现才能提升为 `stable`。
- 版本不可静默覆盖，只能 supersede 或 revoke，历史保持可见。
- 公开发布物使用内容寻址和 Ed25519 签名，客户端拒绝未知 schema 或无效签名。

## Dashboard 约束

- 明示模拟数据、样本层级、有效期和最后更新时间。
- 展示账号、节点、地区、ASN 和时间覆盖。
- 不使用只有“真/假”的二元标签。
- 不按匿名样本总数直接排序提供商。
- 提供商回应与审计证据并列展示，但不覆盖证据。
- 模型别名和具体快照分开，避免别名更新后沿用旧结论。
